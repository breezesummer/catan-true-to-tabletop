# M7 本机联机实现与使用

日期：2026-10-15；当前实现与使用说明更新于 2026-10-17（Asia/Shanghai）。游戏：卡坦岛之三国争霸，当前内测版1.6。本轮为问题修复与联机交互调整，未据此宣布新发行版。

用户本轮确认先完成本机可验证部分，云服务器尚未准备。大厅允许直接加入房间，设置密码时才验证密码；采用持久访客凭据、存档不自动删除。2026-10-17 更新为离线 AI 接管、重连下一次本人行动时交还控制；房间服务运行时，全体人类离线仍继续推进至完局。真实多机、外网部署、清洁机器及长期容量验收仍须后续完成，不将本机检查记为 M7 全阶段完成。阶段退出状态保留在 [路线图](ROADMAP.md)。

## 启动与加入

本轮构建使用 `tools/development/Build-M7.ps1 -OutputRoot .local/lan-repair-20261017`，运行使用 `tools/development/Play-M7.ps1`。当前试玩程序位于 `.local/lan-repair-20261017/Builds/Windows/CatanM7.exe`；须保留整个 Windows 目录，包括旁边的 `Server` 自包含服务目录。现有单人四规则与当前 AI 继续使用同一客户端。

进入“局域网联机”默认显示左侧“房间列表”，自动搜索同网可达的房间；点击“重新搜索”可刷新，选择房间即可加入。左侧“创建房间”保留规则、地图与同桌配置，Windows 点击创建后自动准备随包服务。无需玩家手动核对证书指纹；客户端自动绑定所选发现结果中的证书，实际 TLS 必须匹配，仍不接受任意证书。此流程依赖可信局域网发现环境；防火墙与 Wi-Fi 客户端隔离仍可能阻止发现和连接。

列表中无密码房间直接加入，密码房需要口令；在线入口也保留房间号加入。玩家可以直接换房，无须先结束或退出上一个房间；每个房间分别保留恢复身份，返回旧房间时优先恢复自己的原位置。房主可选择规则、剧本、3／4 人、胜利分数和 AI 建筑颜色；所有人类准备后开始，更改配置后需重新准备。对局开始后新玩家不能抢占原位置，原玩家须用设备安全保存的凭据重连。空大厅结束，无在线人类和已结束的房间不进入公开列表，保留的私有存档不会成为永久显示的历史房间。

玩家名称统一在“设置 → 玩家”填写，本地和联机房间共用，已在房间内也会同步更新。游戏中头像、回合、交易、历史与分数详情显示姓名。AI 从哈基米、吃白饭的大肥鲸、糖包、我是奶龙中随机分配，同房内不重复；建筑颜色与行动顺序分开，先手继续由规则开局掷骰决定，头像按真实行动顺序排列，开局红字提示自己的行动次序。

在线大厅使用相同客户端与协议，填写已部署服务的 HTTPS 地址，按系统信任链和域名正常验证证书。本次没有可提供的公共在线服务器；部署方式见 [服务端说明](M7_SERVER.md)。Windows 可托管随包服务；Android 为加入端，本轮补充 AndroidKeyStore 安全凭据保管，不能启动 Windows 随包服务。Android 真机联机、重连与发布后端尚未作为已验证交付。

## 权威与隐私

- `Catan.Network.Contracts` 为 .NET Standard 2.1 协议与显式类型 JSON 编解码，Unity 与服务共用。协议不接受任意类型名、未知字段、重复字段或非法枚举。
- 本轮协议号为 2，联机双方须使用本轮客户端／服务；旧客户端明确拒绝。既有协议 1 的私有房间存档兼容恢复，下次提交原子迁移；未知未来版本仍拒绝，保留原文件。
- `Catan.Rooms` 适配四种现有规则入口，规则核心和当前 AI 没有复制或修改。每房间顺序处理命令，以认证凭据确定席位，校验控制 ID、规则/场景版本、命令 ID 和预期修订号。
- `Catan.Server` 是纯 .NET 10 服务，通过 HTTPS/WSS 发送各席位的 `PlayerView`，历史按授权席位分页。客户端不实例化本地规则主机，不运行对手 AI，不导出服务器权威存档。
- Windows Unity 6000.3.25f1 / Mono 的实际局域网 WSS 握手未通过，日志为 `UNITYTLS_X509VERIFY_FLAG_NOT_TRUSTED`。客户端自动使用同一严格证书固定的 HTTPS 每秒同步，界面显示当前传输方式；命令与查询仍加密并认证，不关闭 TLS 校验。服务端 WSS 已由独立 .NET 客户端验证，不能据此声称 Unity WSS 通过。
- AI 在服务端只读取所属 `PlayerView`，通过同一规则 `Execute`。不同玩家的弃牌、交易、金矿、进步卡等待决按实际有权行动的席位调度。
- 命令重试先查持久账本，再检查修订号。同 ID 同内容返回原结果与最新本人视图，同 ID 不同内容拒绝。`CommittedRevision` 是原命令提交号，`Revision` 是回复时的当前局面。
- 网络快照最多保留 37 条真实公开事件：最近 32 条、最近回合边界、本回合各席最近一次报价。完整授权历史通过游标分批取得，每页最多 200 条。其他玩家的隐藏手牌、牌库顺序、未揭示地图、随机状态和命令原文账本不进入网络输出或公开日志；本人手牌及规则允许的临时查看信息只发给有权玩家。

局域网服务保管完整权威状态，因此玩家需要信任房主电脑所有者。客户端侧隐藏界面不能阻止房主读取自己电脑上的服务存档。此次沿用已有规则随机算法，不以隐藏种子替代密码学不可预测性保证。

## 保存与故障恢复

方案中的 SQLite 是建议选型。本轮采用完整房间文档的原子文件事务：规则快照、修订号、命令账本、设置、身份哈希及首次加入登记一同写入同目录临时文件，调用 `Flush(true)` 后以 `File.Replace` 提交；首次创建用同目录 `File.Move`。成功后才发送确认。服务目录与房间目录均有独占写锁。`IRoomStorage` 保留后续替换数据库的边界。

此调整减少 Windows 随包服务的数据库依赖，适用于当前单实例、每房间串行写入。每次提交会重写完整房间文档，成本随存档和账本增长；没有数据库查询、跨房间事务、多实例调度或自动备份能力。进程重启和注入的写入失败已有测试，突然断电、底层文件系统及磁盘缓存的持久性仍须在目标部署环境另验，不能从本机检查推导保证。

写入失败后恢复最后已保存状态并暂停房间，不能发布未提交局面。损坏或版本不兼容的存档保留原文件并拒绝启动，不用新局覆盖。已开局玩家主动离开、断线或心跳超时后自动由 AI 托管，包括待决选择；全体人类离线仍继续推进至完局，前提是服务持续运行且未因持久化失败或命令上限暂停。局域网主机关闭或服务停止后，需要原电脑重新启动同一服务目录才能恢复。本期不自动传送存档换主。未开局最后一位人类主动离开后关闭大厅；仅断线时保留默认 45 秒恢复窗口，超时后释放位置并关闭空大厅。

密码使用随机盐及 100,000 次 PBKDF2-SHA256；访客凭据使用随机令牌，服务只保存 SHA-256 哈希。凭据默认有效期 180 天，是当前实现参数，可通过 `RoomDirectoryOptions.CredentialLifetime` 调整。大厅退出会释放席位并撤销该身份；开局后退出保留原凭据、席位和待决。显式 `Revoke` 永久吊销凭据，已经开始的席位继续由 AI 操作，不能重新领取。

重连发放新的连接控制 ID，旧连接随后不能操作或读取该席位。已托管玩家重连后先恢复本人视图与历史，AI 持续操作，直到下一次自己的行动回合才交还控制；开局蛇形摆放按摆放轮次交接，连续两次同色摆放也分别识别。仅替换仍在线的原连接时不额外等待。房间管理权可以转交，也会在管理员掉线或心跳超时后交给在线人类；管理权变更不迁移权威存档，不改变任何玩家的隐藏信息权限。

Windows 客户端用当前用户 DPAPI 保存凭据，Android 加入端补充 AndroidKeyStore 保管。恢复材料按房间分别保存；LAN 使用服务器证书与房间号作为稳定键，同一服务更换 IP 后仍可恢复原身份，在线使用服务地址与房间号。遗失、过期或吊销的凭据不能凭昵称或房间号找回；账号、跨设备身份恢复及人工找回尚未实现。请保留私有服务目录的受限备份，不放入分享包或 Git。

## 首次创建或加入的回执恢复

当前客户端在发送 `Create`／`Join` 前生成随机申请编号 `EnrollmentId` 和 32 字节随机恢复令牌 `EnrollmentCredential`，先将原申请和令牌写入设备安全存储（Windows DPAPI；AndroidKeyStore 路径待真机验收）。第一次响应丢失时，重试保留这两项和完整原申请，不重新生成身份。

服务将申请编号、凭据哈希、申请内容指纹与房间及席位放在同一次持久提交内。内容指纹使用原恢复令牌为密钥计算 HMAC-SHA256，密钥本身不落盘；这避免将含房间密码的申请直接快速哈希后，产生额外的离线密码猜测校验值。

相同申请重试返回同一房间、当前所属席位及当前可见状态，不重复创建或占位；响应不再回传长期凭据。重复响应的 `CommittedRevision` 保留最初申请提交号，`Revision` 表示当前状态。相同编号或令牌用于不同内容会被拒绝；大厅退出、凭据过期或吊销后仍保留登记墓碑，不能通过重试复活失效身份。服务重启后的重复申请和首次写入失败后的重试均有独立测试。

协议仍兼容不带这两个字段的旧验证驱动，其首次响应由服务生成凭据。该兼容流程不具备首次响应丢失后的身份恢复能力，产品客户端使用预存申请流程。此机制只解决同一申请的恢复，不引入账号或跨设备找回。

当前默认限制为 128 个保留房间；每房间最多保存 100,000 次身份申请，人类与 AI 合计成功执行的规则命令也不得超过现有规则存档的 100,000 条恢复上限。达到上限时保留最后已提交局面并拒绝继续推进。限额是保护措施，尚无长期容量承诺。

# B4 联机响应与动画流畅性优化方案

日期：2026-10-25（北京时间）。适用项目：卡坦岛之三国争霸。

状态：**第一批 P0–P3 与第二批 P4／P5 的工程实施完成；前台体验与 P6 收口尚未验收。** 第一批后台／兼容结果见 [第一批验收记录](verification/online-performance-batch1/验收记录.md)，第二批即时推送、席位增量、事件补写、恢复与兼容结果见 [第二批验收记录](verification/online-performance-batch2/验收记录.md)，消息与回退合同见 [席位同步说明](ONLINE_STATE_SYNC.md)。第二批同桌四席响应正文已显著降低，推送等待的 50ms 目标仍有未达标样本；Android 构建与签名通过，模拟器运行被自动审批拦截，不计为真机／运行通过。第一批按用户指定只做后台工程与兼容验证的边界继续有效；四终端、60分钟、弱网、4Mbps真实出口与前台帧率仍留 P6。下文的原始问题判断依据当天约14点的B4现场，受控对照使用的构建各自单列，不将 B4、B5 与本次候选混为同一二进制。本轮沿用2.0.2，只保留本地候选包，不正式发布、不部署云端、不推进M7／M8状态。

## 1. 目标与判断

目标是让联机时的镜头、选牌、拖动和已经开始的动画接近同机本地体验，同时减少点击到操作开始的等待。规则结果仍由服务器确认，网络往返时间无法消除；等待确认期间，客户端应持续绘制并响应不依赖该结果的本地操作。

当前证据表明，客户端收包后的处理和主线程应用存在明显瓶颈。4Mbps 出口会放大多人同时同步时的传输等待，但不能解释已经收齐数据后仍耗费数百毫秒的处理。优先处理客户端和冗余通信，再根据四人实测决定扩容。

本轮优化不改变卡牌规则、合法性裁决、随机结果、资源供应与胜负计算。规则核心继续独立于 Unity、UI、动画和网络；棋盘沿用稳定的 Tile／Vertex／Edge ID。

## 3. 体验合同与数据流

每种操作分别记录输入反馈、权威确认和展示完成三个时间点，不用一个“响应时间”混合计算。

| 操作 | 立即在本机做什么 | 必须等待什么 |
| --- | --- | --- |
| 拖动／缩放镜头 | 下一帧更新镜头与必要裁剪 | 不等待网络、历史或动画队列 |
| 选牌、悬停、抬起棋子 | 选中、描边、拖动预览和待确认提示 | 不提前提交规则结果 |
| 打牌、建造、移动落点 | 立即显示已提交；防止同一操作重复提交 | 服务器确认后扣费、落定、揭示结果 |
| 收牌、其他玩家打牌 | 收到有权限的确认事件后连续播放 | 不预测未知牌面或随机结果 |
| 服务器拒绝 | 清理待确认状态，恢复可操作并显示原因 | 不保留错误扣费或虚假成功画面 |
| 弱网／短断线 | 镜头与已有动画继续运行，显示连接状态 | 依赖新权威结果的操作保持受控 |

目标数据流：用户输入 → 本地反馈 → 提交命令 → 服务器校验并持久化提交 → 回执与席位可见事件 → 后台接收／解码 → 原子更新客户端数据 → 按顺序播放展示。

“原子更新数据”与“分帧更新画面”需分开：不能为了降低单帧成本，把同一修订的手牌、资源和棋盘拆成互相矛盾的可操作状态。后台产物不可变；主线程一次切换完整逻辑视图，再按预算处理显示对象。展示未赶上时，相应交互仍按明确条件受控，镜头不随之锁死。

### P0：固定基线并拆清等待

交付：同一场景的本地、回环联机、云端对照，以及输入至动画开始的分段时间线。

1. 记录客户端构建标识、程序集指纹、服务端构建、规则包、地图、人数、分辨率、图形接口、垂直同步及限帧设置。版本字符串相同不代表程序相同。保留当前工作区已有 B5 和 Android 修复，避免把未提交工作误当作 B4。
2. 使用独立测试目录和房间留存同一中后期局面；身份凭据、隐藏信息和存档只在受控本地留存，公开报告只放聚合指标。
3. 在已有诊断上增加必要阶段：正文收齐、解码入队、工作线程开始／结束、主线程入队／开始／结束、首帧展示。用同一客户端单调时钟和请求编号关联；跨机器时间戳不直接相减当单程延迟。
4. 记录线程池／解码队列深度、解码期间分配量、GC、主线程阶段和焦点。若主要是工作线程排队，优先治理并发与队列；若主要是解析，优先替换转换路径；两者可同时存在。
5. 正常日志继续白名单、有界、后台写盘；详细逐帧采样仅在诊断窗口启用。诊断启动失败不能阻断游戏或回包应用，保留已修复的 Android 构建标识兼容路径。

退出条件：能将一次慢操作分到收包前、后台调度、解码、主线程排队、应用和动画等待；同一测试条件可重放，不依赖隐藏窗口结果。

### P1：解码与主线程应用

交付：收齐数据后不再常态等待数百毫秒；应用状态不再阻塞整帧。

1. 建立约 10KB、70KB、250KB 与长局大历史的合成／脱敏数据基准，分别测首次和预热后、串行和并发时的耗时与分配。尺寸是测试档位，不声称当前所有操作均达到这些大小。
2. 对现有 JSON 线格式先做兼容替换，采用直接 JSON 读取与明确类型映射，减少 XML 树、字符串往返和反射。实现选型以项目依赖、Unity Mono 与 Android IL2CPP／AOT 实测为准，不在方案阶段绑定未经验证的新库。
3. 保持类型白名单、深度／长度限制、枚举与字段校验、空值与缺省值语义；覆盖内部 setter、可选三国字段和未知／重复字段。新旧解码结果必须一致，不能以宽松解析换速度。
4. 后台一次准备响应、玩家视图及所需历史，不能在后台操作 Unity 对象。以连接代次、房间、对局编号和修订过滤迟到结果，避免重连或重开后的旧任务覆盖新局。
5. 解码工作采用有界并发与明确背压，避免每个包无限创建任务。WebSocket 收包与耗时解析可解耦，但接收队列须有界且有字节上限；队列饱和时按消息类型背压或进入可恢复重同步，不能无界缓存或悄悄丢确认。
6. 历史按稳定编号／技能事件 ID 增量维护。B4 同一命令可能产生多个技能事件，同一技能事件又可能补充结果，必须支持去重与替换，不能仅凭命令序号去重。缓存失效键包含历史内容版本，不仅是条目数或最大序号。
7. 主线程切换准备好的数据，显示更新拆成小任务；以实测开销约束单任务，而不是仅在大回调结束后检查 4ms。状态合并只用于可替代的状态快照，命令回执、关键展示事件与历史游标不能随之丢弃。

初始目标：约 70KB 常见回复预热后，后台调度＋完整必要解码 P95 ≤20ms；稳态网络显示应用 P95 ≤2ms、P99 ≤4ms。首次入桌、全量恢复和资源预热单独列账。超标时提交阶段归因，不宣称仅搬后台就完成优化。

### P2：低风险通信瘦身

交付：删除明确不被使用的重复数据，先降低解析和 4M 出口负担。

| 消息 | 目标内容 | 一致性要求 |
| --- | --- | --- |
| 操作预览 | 合法性、原因、请求编号、判断所依据的修订 | 服务端执行仍重新校验；旧修订预览失效 |
| 心跳 | 会话存活、当前修订、必要恢复提示 | 不因去掉快照而破坏活跃续期、超时检测与 HTTP 降级 |
| 历史分页 | 请求范围内的可见历史、游标、是否还有后页 | 不重复附带近期历史；水位完整且不遗漏多事件命令 |
| 命令回执 | 命令编号、成功／拒绝、已提交修订与必要结果 | 不能仅收到回执就假定对应可见状态和事件已应用 |

先落实预览和历史去重，再处理心跳与精简回执。回执先到或状态先到都须有明确状态机；不能依赖“某个完整回包偶然补齐状态”。新增消息能力需协商，旧客户端保留旧回复形状或明确不支持，不能静默改变所有客户端依赖。

目标：普通预览／心跳回复正文通常 ≤2KB；相同脚本的总响应字节显著下降，建议以第一批较基线降低至少 50% 作为测量目标，不能仅以消息数下降作为通过依据。

### P3：界面、镜头与动画

交付：动画每帧主要做插值和绘制，不重算整局信息。

1. 缓存 GUIStyle、GUIContent、费用文字、玩家摘要和手牌布局。缓存按局面修订、展示水位、选择状态、窗口尺寸及设置变化失效；鼠标悬停仍及时响应。避免 Layout 与 Repaint 重复整理同一份数据。
2. 展示模型只消费新到或发生替换的事件，停止在每帧绘制中扫描整局历史。长局历史界面只处理可见部分，完整历史按既有分页机制读取；不能为了省内存删除规则展示必需的事件。
3. 动画开始时缓存 Renderer、材质引用、路径与端点，播放中避免层级搜索、数组复制和频繁分配。对飞牌及临时效果建立有上限的对象池，返回时重置材质、颜色和回调。Unity 的对象复用依据见[官方说明](https://docs.unity.com/en-us/engine/6000.3/manual/analysis/performance-memory/managed-memory/optimizing-code-managed-memory/reusable-code)。
4. 入桌阶段预热本规则包会用到的卡面与效果，限制内存预算；不能一次加载全部主题和全部高分辨率资源。首次展示与稳态分别测量。
5. 缓存地图边界、投影所需静态数据和镜头限制，平移主要更新变换；窗口、地图、缩放等确实影响拟合时才重算对应部分。保留输入命中、边界限制和触控行为。
6. 正常对局不靠缩短动画掩盖性能问题。动画按本地时间连续播放，新状态到达不从头重启动画。事件等待队列有界；恢复积压时进入明确的恢复模式，补齐必要状态与事件，不把几十秒旧装饰动画逐一堵在交互前面。
7. 避免将所有输入都绑定到“有动画正在播放”。仅锁住会与当前权威／展示阶段冲突的操作，允许镜头和查看信息；不放开需要规则等待的操作。
8. 完成 CPU 与分配优化后，如果逐帧分析仍显示 GPU 限制，再按实际 Pass 成本调整材质、阴影、后处理或分档。当前不据 D3D12 提示直接更换接口，也不先降画质。

目标：同场景 GUI 与持续分配明显下降，稳态热点无不必要逐帧分配；镜头和已启动动画不因同步停顿。具体 GUI／GC 子预算在 P0 固定硬件后确定，最终以整帧与交互门槛验收。

### P4：事件触发的即时推送

交付：其他玩家的动作无需等待下一个 750ms 检查点。

1. 权威命令成功持久化提交后通知订阅者；AI、超时推进、房间控制状态变化也走同一通知机制。拒绝操作只回复申请者，不制造虚假状态变更。
2. 房间锁内只登记变更版本与通知意图，网络发送在锁外。席位投影使用稳定的已提交状态，不能读到一半更新的数据。
3. 同一修订、同一权限席位可复用投影结果；不可把含私人信息的序列化结果跨席位复用。将同一短窗口内的多次通知合并为最新状态，但关键事件仍按序传递；合并窗口可从约 10–20ms 起测，不作为固定规则延迟。
4. 保留周期兜底、轻量心跳、HTTP 回退与自动恢复 WS。处理订阅建立和提交同时发生的竞态，连接完成后检查修订缺口，避免漏掉首次通知。
5. 回执优先、慢客户端隔离、有界队列继续有效。服务器不能因一名玩家接收慢而拖住其他席位或权威执行。

目标：正常负载下，从提交完成到消息进入发送队列的额外推送等待 P95 ≤50ms；该指标不包括公网传播与客户端解码。以服务器同一计时域测量，不能把未经校时的跨端时间相减。

### P5：按席位的增量状态与可靠展示事件

交付：普通动作不再反复传完整地图和大段历史。

1. 拆分连接控制、首次快照、状态增量、展示事件和历史补齐。静态地图按地图版本发送；雾岛未公开内容不在“静态缓存”中提前泄露，发现新地块时仅补该席位获准看到的变化。
2. 增量带房间／对局编号、基准修订、目标修订及增删改项。按稳定 Tile／Vertex／Edge／玩家／实体 ID 定位，明确删除语义；玩家私有手牌、选择项和武将信息只能来自该席位投影。
3. 客户端仅在基准匹配时应用增量。缺包、版本不符、重开或身份轮换时暂停依赖该状态的提交，取得完整快照再恢复；重复和迟到包不得回退局面。
4. 状态修订与展示事件水位分别维护。快照至少说明覆盖到哪个完整事件范围，避免状态已前进但扣费、出牌或收牌展示缺失。B4 保留稳定技能事件 ID 和内容更新语义，不假设一条命令只有一个不可变事件。
5. 只有中间状态可以合并；已确认事件去重后有序消费。长时间断线可恢复到权威最终状态，并按产品约定展示恢复摘要和必要结果，不重播全部旧动画；此策略须单独验收。
6. 保留初次加入、缺口恢复与兼容旧客户端的全量路径。通过能力协商或协议版本区分消息，避免新字段直接进入旧严格解码器；如果无法做到安全兼容，就明确要求对应客户端更新。
7. 是否增加压缩由包大小、CPU、分配和线上字节的对照决定。小消息不必压缩；不能只减少传输字节却把 CPU 峰转移到主线程。二进制协议不作为首批前提。

初始容量目标：相同四席动作脚本的应用层总响应字节比 B4 基线降低至少 70%；4Mbps 限制下普通对局无持续发送积压，正常稳态 1 秒出口窗口 P95 争取 ≤2Mbps。初次同步、重连和大历史补齐单独统计峰值与恢复时长，不混入稳态指标，也不能隐藏其影响。

## 5. 测试矩阵与验收口径

### 5.1 复用工具与分层验证

复用 [诊断收集](../tools/validation/Collect-M7Diagnostics.ps1)、[诊断汇总](../tools/validation/Summarize-M7Diagnostics.py)、[逐帧汇总](../tools/validation/Summarize-M7FrameProfile.py) 和 [网络检查](../tools/validation/Test-M7Network.ps1)。既有性能工具可复用采样方式，不以本方案恢复已搁置的 Ultra 主题计划。

相关测试优先从 [客户端测试](../tests/Catan.Server.Tests/OnlineClientTests.cs)、[诊断测试](../tests/Catan.Server.Tests/ClientCommunicationDiagnosticsTests.cs)、[帧计时测试](../tests/Catan.Server.Tests/FrameCostDiagnosticsTests.cs)、[协议审计](../tests/Catan.Network.Tests/WireContractAuditTests.cs)、[房间测试](../tests/Catan.Network.Tests/RoomDirectoryTests.cs)、[B4 房间](../tests/Catan.Network.Tests/ThreeKingdomsB4RoomTests.cs)、[B4 历史](../tests/Catan.Rules.Tests/ThreeKingdomsB4HistoryTests.cs) 和 [展示测试](../tests/Catan.Rules.Tests/TabletopPresentationTests.cs) 中选择。

文档阶段只查链接和差异。局部缓存或解码修改只跑相关检查与必要程序验证；P4／P5 属于跨模块同步变更，才扩大到四端、恢复和权限回归。仅对新增行为和现有覆盖缺口补测试；没有新改动、失败或未解决风险时，不重复全量构建。

### 5.2 必测场景

| 场景 | 观察内容 | 必须保持的结果 |
| --- | --- | --- |
| 静止棋盘、持续拖镜头 | GUI、GC、镜头帧时间、空闲流量 | 不因保活和无变化同步周期卡顿 |
| 多人同时收牌 | 首帧延迟、连续飞牌、手牌落位 | 数量与牌面权限正确，不重复／漏播关键结果 |
| 本人及别人出牌 | 点击反馈、回执、揭示、动画起播 | 确认顺序正确，拒绝与取消能恢复 |
| 移动棋子与连续预览 | 预览字节、应用耗时、位置插值 | 拒绝落点不提交，合法落点与权威一致 |
| B4 连锁／多步技能 | 同命令多事件、历史更新、待决 | 去重不吞事件，替换不导致动画重复 |
| 中后期大手牌／长历史 | 每帧分配、历史合并和滚动成本 | 局长增长不导致每帧全量工作持续增长 |
| 雾岛揭示及地图变化 | 局部更新、首次资源加载 | 未公开地块保密，已揭示状态一致 |
| 回执与状态先后颠倒 | 待确认状态和应用水位 | 不重复提交，不提前开放冲突操作 |
| 重复／迟到／缺口 | 去重、恢复、旧代次过滤 | 不回退、不重复扣费、不泄露其他席位 |
| 断线、切房、重新开局 | 旧任务与新身份隔离 | 原有控制权、幂等与恢复合同不退化 |

使用相同地图、规则包和动作脚本比较本地、回环、局域网与云端。客户端构建版本和服务器版本各自固定，不能把换机器、换画质、暂停 AI 或切后台造成的变化算成优化收益。

最终四端测试使用四台独立设备或分别报告硬件；一台 PC 开四客户端只能证明多连接行为，不能代替四机帧率结果。基线先测代表性普通局与最重局，收口再覆盖受影响的基础版、扩展和三国组合路径。

网络条件至少包括正常网络、服务器总出口 4Mbps、100／200ms RTT、受控抖动、轻度丢包和约 3 秒短断网。网络整形放在测试环境，不直接干扰生产房间；使用 TCP／WS 时，丢包预期表现为重传和延迟，不假设消息自动无损按时到达。

### 5.3 初始验收门槛

下列是实施目标，不是已达成结果。PC 基于固定目标硬件、1080p、明确的 60FPS 设置；Android 保持兼容并单独测量，不套用 PC 性能结论。

| 维度 | 初始目标 | 测量边界 |
| --- | --- | --- |
| 本地交互 | 镜头、悬停、选中下一帧反馈；输入至首个反馈 P95 ≤50ms | 不把权威确认或完整动画时长混入 |
| 后台处理 | 常见约 70KB 回复的调度＋完整必要解码 P95 ≤20ms | 同时报告排队与纯解析、冷／热、分配量 |
| 网络主线程应用 | 稳态 P95 ≤2ms、P99 ≤4ms | 同时报最大值和 ≥50ms 异常，不用均值掩盖峰值 |
| 整帧 | 帧间隔 P95 ≤18.3ms、P99 ≤25ms | 前台完整 HUD；同步处理不得造成 ≥50ms 长帧 |
| 长帧 | 稳态 ≥50ms 帧比例目标 <0.1%，约 100ms 以上峰逐一说明 | 开局加载、后台、退出分组保留，不事后删除异常 |
| 推送等待 | 提交完成至入发送队列 P95 ≤50ms | 单独统计服务、发送、网络与客户端，不混算 |
| 带宽 | 相同四席脚本总响应字节降低至少 70%，稳态留约 50% 的 4M 出口余量 | 同时报应用字节、网卡出口、1 秒峰及全量恢复峰 |
| 队列与长局 | 所有队列有界；恢复后积压消退；内存无持续无界增长 | 至少 60 分钟四端运行并覆盖中后期局面 |
| 正确性 | 重试不重复执行、四端公共状态一致、私有信息隔离、断线后恢复一致 | 必须通过，与性能指标同时成立 |

短动作基准每类建议至少 30 次，记录样本数；整体 P99 需要足够长的逐帧采样，不能拿几十次操作的 P99 冒充稳定统计。重复测量用于确认变更收益或调查波动，不作为无理由反复构建。

若本地相同局面本来就不达帧预算，先明确本地瓶颈并在相同画质下比较联机增量成本，不能把两者都卡称为“联机与本地一样流畅”。最终报告需同时交付绝对体验指标和相对改进。

## 6. 容量、部署与回退

现有证据不支持先重构持久化、取消磁盘确认或大改 AI。服务端锁与保存作为监测项保留，只有四人或多房间测试证明其成为瓶颈时，再单独立项；不能先回执成功再异步落盘而降低已承诺的恢复可靠性。

扩容决策在优化后做：如果目标房间数下真实出口仍频繁接近 4Mbps，且发送排队随之增长、其他处理阶段已达标，则比较更高带宽的同条件结果。按优化后每房间峰值、同时活跃比例和约 50% 余量规划容量，不能用单房平均流量直接推算支持多少房间。提高带宽只能缩短受传输限制的部分，不能替代客户端达标。

每个工作包形成独立提交与前后数据。实施时先保全现有工作区，在明确基线或隔离工作副本完成；不得恢复、覆盖或顺带提交正在开发的其他功能。代码修改完成后按项目约定提交并推送，报告准确提交范围。

部署分为候选包、本机／测试服务、兼容性验证、真实四端验收和云端切换。云端切换避开活动对局，保留旧程序与必要备份。涉及协议能力时先验证旧客户端对新服务、新客户端对旧服务、新旧混用，无法兼容的组合明确提示更新。

至少保留旧解码／旧同步的可控回退路径，回退标志不进入普通玩家操作流程。关闭增量模式时先重新取得完整状态，不能把已有增量缓冲直接交给旧逻辑。回滚服务时同时核对协议和存档兼容性；本方案优先不改变权威存档格式，便于回退。

出现状态分歧、隐藏信息暴露、重复扣费、恢复死锁或显著长帧回归时，停止扩大部署，回到上一通过的候选版本。回退不丢弃用户当前存档，也不默认恢复旧备份覆盖新进度。

正式发布仍按 AGENTS.md 的版本、PC／Android 双端及 `game version/release` 规则执行。性能候选包、服务器部署和正式发布是分别记录的动作，本次写方案不触发其中任何一项。

## 7. 最终交付清单

- 基线与候选构建标识、硬件／图形／网络条件、相同场景与操作脚本。
- 请求各阶段 P50／P95／P99／最大值、前台慢帧分布、主要调用栈及分配来源。
- 四席应用字节与真实出口、推送等待、队列峰值、恢复时间和容量结论。
- 对应范围的自动测试、四终端可见窗口、长局与弱网结果；未完成项单独列出。
- 命令幂等、技能事件去重／替换、席位隐私、重连和新旧协议兼容证据。
- 各工作包提交、部署／回退步骤，以及按日期写入《农场主手记》的实施与验证记录。

推荐从 P0 开始，随后完成 P1、P2、P3 的第一批验证，再进入 P4／P5。第一批的退出标准是客户端处理和动画已有可测改善；第二批的退出标准是四人同步等待与带宽确实下降，且完整恢复与权限合同不变。

## 确认并修复的问题

1. **重复全量传输**：每秒 WebSocket `Get` 会返回完整玩家视图与近期展示记录，同时服务端每 750ms 检查并推送变化。将保活改为每 10 秒一次，变化推送周期保持不变。
2. **临时传输断开错误触发 AI 接管**：旧 WS 在清理时立即 `Disconnect`，会影响已恢复的 HTTP 或新 WS。改为由真实客户端请求的 45 秒活跃宽限判离线，主动 Leave/Revoke 仍立即执行。
3. **服务端推送替失联玩家续命**：内部推送也调用 `Get` 并刷新 `lastSeen`。明确区分内部投影读取和真实客户端活动，失联者仍会按超时处理。
4. **积压快照挤占回复队列**：回执保序优先，未发送的全量推送合并为最新一份；避免普通状态积压消耗全部回执队列。发送期限改为 10 秒，并记录排队、发送与关闭原因；溢出/断线后的命令仍依靠原编号去重重试。
5. **网络任务依赖 Unity 帧调度**：HTTP 接收与完整响应解码、WS 收发及保活在后台完成，仅将局面应用排入主线程。主线程每帧最多 32 回调或约 4ms；单个回调不能被中断，首次建桌仍可能超预算。
6. **WS 降级后不恢复及旧身份竞态**：增加 12 秒专属心跳回执期限与 2–30 秒恢复退避；HTTP 重连轮换连接身份后，新 WS 立即替换旧建连，旧回包、关闭和完成回调按代次过滤。修复迟到 HTTP 回包错误覆盖 WS 状态标签。
7. **切房确认竞态**：完成绑定和旧房清理后再发成功回执，防止客户端已收到切房成功而旧席位仍显示在线。

没有修改游戏规则、动画时长或图形 API。输入等待与动画卡顿新增诊断：连接、命令回执、房间请求、历史补齐、卡牌/骰子/棋子动画、AI 控制权，以及每 5 秒帧窗口、GC 与限频尖峰。日志字段、保留上限和收集步骤见[诊断使用说明](../../ONLINE_DIAGNOSTICS.md)。

### 四席真实 WebSocket 对照

同一台机器上的四条真实 WS 连接，同一个新服务器、同一个四人双扩展“驶向新海岸”静止开局棋盘，分别采集约 21 秒。这是同步节奏对照，不是旧服务器二进制回放。

| 节奏 | 接收消息 | 接收字节 |
| --- | ---: | ---: |
| 每秒 Get | 84 | 2,078,307 |
| 每 10 秒 Get | 12 | 296,901 |

窗口内接收字节降低 **85.7%**。随后停止主动 Get，提交真实合法建村，其他三个席位仅通过服务端推送收到新建筑，延迟约 **118 / 122 / 751ms**。数字受 750ms 推送检查相位影响，不是公网延迟承诺，也不能直接换算为完整对局或动画 FPS 的提升。公开证据见 [four-seat-ws-measurement.json](four-seat-ws-measurement.json)。

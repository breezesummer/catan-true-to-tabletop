# U0 CPU异步峰与优化重点

日期：2026-10-21；构建 Catan1.7.1。本文补充 [U0基线](U0-baseline.md)。固定本机、D3D11、1920×1080、真实桌游、四局面与原相机路线，规则与AI暂停。完整采样区间保留原始行，不事后删尖峰。

## 约61毫秒峰的来源

在开发构建、不排空时序的对照中，拥挤局复现 **61.6175 ms** CPU峰：`crowded/frames.csv` 的 frame=2（第三个读数），CPU主线程61.3651 ms、渲染线程2.2633 ms、Present等待0.2432 ms、GPU16.97808 ms，而这一行的Stopwatch帧间隔仅15.054 ms。

`preparation.json` 同时记录采样前准备61.6527 ms，其中 `ExportEnvelope()` 导出权威信封47.0898 ms、采样数组分配0.6223 ms，其余含计数器启动、工作集查询及一次帧等待。导出结果只在本地内存中用于前后相等检查，不写入公开性能证据。

旧工具预热后才进行上述准备，随后仅跳过一帧就开始读 `FrameTimingManager`。GPU/CPU异步返回仍会带回准备帧，因此「当前采样帧间隔」与同一行的「异步CPU时序」不是同一个源帧。此次第三行的峰与准备阶段吻合，且后一条原始时序时间戳跨越61.6175 ms；不是相机路线进入拥挤区后突然多做了61毫秒几何渲染，也不能直接归因于GC停顿。

本轮用同一程序、夹具、相机分别运行 `DrainFrames=0` 和 `16`；后者在准备后继续请求并消费16帧，再开始稳态统计。准备耗时单独保留，避免将测量开销隐藏成游戏性能改善。GUI计时、GC计数与异步FrameTiming仍有相位差，只比较区间分布，不能把单行数据强行相减。

这解释了可复现的同类约61毫秒起始峰；原先那一轮的原始61毫秒文件未在本轮工作区中找到，不能宣称拿到了其原始调用栈。此次不是减少游戏加载耗时的优化，只是补齐测量边界与归因证据。

## 数据口径与有效性

- `cpuMainMs`、`cpuRenderMs`、`presentWaitMs`、`gpuMs` 来自同一返回的 FrameTiming；原始时间戳用于去重和检查连续性。依据当前安装Unity 6000.3 API，单位毫秒，各项有重叠，不能相加为CPU总耗时。
- Stopwatch与Unity时间戳即使频率相同也不保证同一原点。本机两者原点不同；`sampleStartStopwatchTicks`仅供同计时器复现，不直接从Unity时间戳减去它。
- `guiMs` 汇总 M2/M3/M4/M5/M6 已有 `FrameCost.Stage.Gui` 范围，包含每帧IMGUI各次事件；`gameUpdateMs` 只覆盖 M6 Update，不代表全部脚本。CPU/GPU分布可提示瓶颈，不是逐渲染Pass的GPU耗时。
- 开发构建的 `GC Allocated In Frame` 返回有效字节数；普通构建在本机不可用，记为null。主线程 `GC.GetAllocatedBytesForCurrentThread()` 经4096字节哨兵检验仍返回零，标记不可用（CSV为-1），不能用零分配替代缺失数据。
- GC分配是累计新分配，不是净堆增长。Mono三个CollectionCount相同，不作为三代独立回收次数相加；其起点在排空前，包含准备后的1+drainFrames帧，不据此精算稳态回收频率。进程WorkingSet返回0，不解释为实际零内存；Unity allocated/reserved/mono与纹理驻留仍保留。
- 目标帧率60，但vSyncCount=1，实测普通图约140帧/秒；不得声称已经锁60。后续应明确限帧策略，帧间隔预算仍按P95≤18.3ms检查。
- 隐藏窗口实验没有持续渲染且超过采样容量，完整性检查拒绝通过；最终改用可见窗口，逐帧记录焦点与相机回调。早期扩容排查与并行构建时的探索数据不计最终基线。截图通过独立相机请求生成，仅证明棋盘，不能代替HUD交互验收。

Unity语义参考：[FrameTiming 6000.3](https://docs.unity.com/ja-jp/engine/6000.3/script-reference/unityengine/frametiming)、[分配追踪](https://docs.unity3d.com/jp/current/Manual/performance-track-garbage-collection.html)。GPU FrameTiming包含提交至完成之间的活动和空闲时间，不能据此断言SSAO或阴影就是GPU主因。

## 后续优化顺序

1. **先处理稳态GUI与托管分配。** 拥挤局GUI范围明显高于普通局，M6 Update自身很小。按公开视图修订缓存布局、玩家／费用字符串与派生列表，缓存GUIStyle/GUIContent，避免Layout和Repaint重复计算相同数据。用开发包的分配调用栈继续细分到函数；当前全帧GC计数不能把全部字节强行归给GUI。优化验收必须保持人类可见投影、待决选择和鼠标预览正确。
2. **随后处理绘制调用和组件密度。** 对比普通与拥挤局的drawCalls、材质槽、三角形数量，优先HUD／棋子共享材质、重复组件复用、按屏幕占比简化。先用Frame Debugger/逐Pass GPU采样确认阴影、SSAO与HUD各占多少，再决定调整4K阴影、全分辨率SSAO或MSAA；本轮没有逐Pass归因证据，不先盲目削地形质量。
3. **将存档导出与加载准备列为独立瞬时预算。** 47毫秒导出在采样前只做一次，不是稳态每帧成本。后续存档／主题切换验收分别测导出、重建、资源释放峰值，不拿异步回传行冒充稳定帧。
4. **固定限帧后再加ultra动态。** 复核60FPS模式，给环境动画保留CPU和GC预算；Android机型及热稳定仍待真机。四局面暂停基线不代表AI、联机或多人连续建造的完整性能。

## 复测入口

先用 `tools/development/Build-M6.ps1 -DevelopmentProbe -OutputRoot <诊断目录>` 构建开发包；普通包不传该开关。执行 `tools/validation/Measure-UltraBaseline.ps1 -Player <程序> -OutputDirectory <新目录> -VisibleWindow -SampleSeconds 15 -DrainFrames 0`，再次用16对照；普通包用30秒、16帧。最后用 `Summarize-UltraBaseline.ps1 -RunDirectory <目录> -Output <汇总json>` 计算P50/P95/P99及峰值。

必须顺序运行，采样期间不同时构建或启动其他游戏；保留原始CSV、启动参数、构建标识、summary、preparation与result。权威夹具继续只保存在.local，不提交其牌库、随机状态或隐藏地图。

# U0 PC 可见窗口性能复测

日期：2026年10月21日。版本：1.7.0；待测代码提交：`e58b314`。用户明确授权打开游戏窗口自动采样后执行；本次没有修改或重建游戏代码。棋子升级另行补入实施方案，尚未制作新资产。

## 结论与可比性

第 2、3 轮构成两轮相同条件的前台基线：四局各采样 30 秒、预热 8 秒，每局 1,801 条数据，焦点覆盖率 100%，持续相机渲染有效，采样前后权威存档完全一致。四类局面 P95 均低于 18.3 ms，同局两轮 P95 最大差 0.0736 ms，没有帧间隔超过 50 ms 的样本。

第 1 轮同样持续渲染，但焦点覆盖率为 0%，保留为可见后台对照。为避免将不同焦点条件当成重复测量，在两轮初始采样后追加第 3 轮。三轮共 21,612 条帧数据、48 张棋盘相机截图；其中前台对比共 14,408 条。

三轮硬件、实际分辨率、图形 API、画质、EXE／四个程序集校验值和夹具一致。配置为 i5-14600KF、RX 9070 XT、1920×1080、Direct3D11、`TabletopPipeline-v005`、MSAA 4、渲染比例 1、目标 60 FPS、VSync 1；现有质量档名 `Ultra` 不代表豪华典藏版主题，当前仍为真实桌游。

这些结果确认的是暂停规则与 AI 的固定镜头短测门槛，不能外推正常对局 CPU、触控操作、多人动画叠加、30 分钟热稳定、内存泄漏或 Android 性能。60 FPS 目标与垂直同步下，帧间隔接近 16.67 ms 也不能证明没有性能瓶颈或仍有多少硬件余量。

## CPU／GPU、绘制与内存

第 2、3 轮 CPU 和 GPU 的有效时序覆盖率均为 100%。第 1 轮拥挤局 GPU 为 1,797／1,801（99.7779%），其他局 CPU／GPU 为 100%。时序由异步 `FrameTimingManager` 提供，可能包含同步等待，不能按 CPU／GPU 数值大小直接判定纯计算负载，也不能假定同一 CSV 行的三种时间属于同一个渲染帧。

拥挤局的 CPU 时序最大值分别为 **64.2925 ms（后台第1轮）、61.6912 ms（前台第2轮）、61.0255 ms（前台第3轮）**。这些原始值保留，不用帧间隔的较小最大值替代。起始样本的异步时序归属和具体原因仍须进一步剖析；不能据此断言 GC、某段脚本或模型造成了同等长的可见卡顿。

第 1、2 轮的该 CPU 峰均出现在第三条数据：累计采样时间约 38.7／39.4 ms，同条帧间隔仅 12.6224／13.2531 ms，且随后没有其他 CPU >50 ms 的样本。峰值时长大于此前采样累计时间，与起始附近旧时序延迟返回相容；CSV 未保存 `frameStartTimestamp`，不能确认具体来源。各轮的独立复算和第三轮检查见 [independent-review.json](independent-review.json)。

第 2、3 轮拥挤局 GPU 最大时序分别为 22.13418／19.32076 ms。第 1 轮日志出现 DXGI `GetFrameStatistics` 时间戳异常，Unity 转用 CPU 侧 delta；第 2、3 轮没有该日志。这也是不把首轮当作前台复测依据的原因之一。

两轮顺序固定为普通 → 最大 → 拥挤 → 迷雾，驻留缓存和采样缓冲包含在内存读数中。前台可执行完整窗口绘制，其资源加载状态与隐藏截图模式不同，不能将二者内存差值认定为泄漏。

GC 分配计数器全程不可用，覆盖率 0，分配总量与已观测量为 `null`；进程工作集返回 0，同样不能作为有效占用。GC 次数摘要来自采样区间外侧的起止读取，CSV 首末行不包含完整边界，不能宣称其总数已由 CSV 精确复算；三代同值也不能相加当作独立收集次数。

## 后续定位方向

当前测试中拥挤局有最多绘制调用、三角形和内存峰值，应优先用它检查棋子／材质的渲染通道、阴影、UI 绘制及模型复杂度。最大地图的格数最多，但并非本组绘制量最大的局面，不能只用最大地图替代拥挤局验收。

这只是后续剖析优先级，尚未定位具体 CPU／GPU 瓶颈。需要进一步取得可解释的逐帧分配数据与 GPU／CPU 分项剖析，确认起始异步时序峰的归属，再冻结 ultra 的模型和材质预算。本轮保持 VSync 与目标帧率不变，没有为了展示更高 FPS 而改变对照条件。

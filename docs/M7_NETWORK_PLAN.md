# M7 局域网与在线大厅联机方案

日期：2026-10-15（Asia/Shanghai）。游戏：卡坦岛之三国争霸。

M7 采用一套纯 C# 权威房间逻辑，分别运行在局域网房主电脑和在线云服务器上。Unity 客户端提交操作并显示自己有权看到的局面；规则裁决、随机结果、AI 和存档由房间服务负责。两种联机方式共用协议、规则和恢复机制。

本文件最初为方案，随后用户要求实施，并确认：暂未准备服务器，先完成本机可验证部分；玩家可直接加入房间，设置密码时需口令；采用持久访客身份、掉线等待、存档不自动删除。房间可列入大厅，也可仅凭房间号加入，不要求额外邀请凭证。云服务商、域名和真实外网验收仍未确定。

当前代码已落地共享协议、权威房间、服务端和 Windows 客户端，具体交付与证据以 [实施说明](M7_IMPLEMENTATION.md) 和 [验收记录](M7_ACCEPTANCE.md) 为准。下文保留原方案的任务和完整验收标准；存储采用同目录原子文件提交而非建议的 SQLite，该差异及边界已记录。真实多机、广域网、清洁环境和长期容量验证尚未完成，按项目约定保留 [路线图](ROADMAP.md) 阶段状态。

## 需求与范围

沿用当前 Windows 客户端、3–4 个游戏席位，以及基础版、航海家、城市与骑士、已支持的双扩展组合。人类和当前 AI 可以混合占据席位，首个联机切片可以从基础版开始，M7 收口须覆盖当前全部规则包和支持的剧本。

| 范围 | 首期目标 |
| --- | --- |
| 局域网 | 创建房间、同网段发现、IP 手动加入；不依赖互联网或云账号 |
| 在线大厅 | 房间列表、创建房间、房间号加入、密码房；显示规则、剧本、人数与房间状态 |
| 房间准备 | 选座、准备、当前 AI 补位、规则和胜利分数设置；配置改变后重新准备 |
| 对局 | 所有操作经同一规则入口；每个客户端只获得自身权限内的视图和历史 |
| 恢复 | 掉线重连、原席位恢复、待决继续、服务器存档续局 |
| 版本 | 加入前检查网络协议、规则与场景版本；不兼容时明确拒绝并提示更新 |

这里的大厅指游戏内浏览和加入房间，不预设已经面向陌生玩家全面公开运营。排位、跨平台、5–6 人扩充、观战、语音和好友社交系统另行规划。局域网与在线模式首期不支持同一局中无缝互切。

原[项目简报](PROJECT_BRIEF.md)将公共大厅列为后续范围；本次将在线房间大厅纳入 M7 方案，排位和商业发行仍保持独立。

## 架构与技术选型

| 层次 | 建议实现 | 职责 |
| --- | --- | --- |
| Unity 客户端 | 现有 Unity 6000.3.25f1 工程 | 输入、合法目标预览、本人视图、动画和网络状态提示 |
| 共用规则 | 现有 Catan.Core，.NET Standard 2.1 | 规则验证、权威状态、稳定 Tile／Vertex／Edge ID、保存恢复 |
| 共用 AI | 现有 Catan.AI，.NET Standard 2.1 | 仅从所属 PlayerView 决策，只维护当前策略 |
| 房间逻辑 | 新建纯 C# RoomSession | 席位绑定、顺序处理命令、AI 调度、重连、持久化 |
| 网络服务 | ASP.NET Core／.NET 10 LTS | 大厅接口、连接管理、消息验证、房间生命周期 |
| 通信 | HTTPS＋WebSocket／WSS，显式 JSON 消息 | 大厅请求和可靠消息传输；心跳、重连由应用层处理 |
| 存储 | 首期单实例 SQLite | 事务保存权威快照、命令结果和房间恢复元数据 |

建议新增的工程边界为 `Catan.Network.Contracts`、`Catan.Rooms`、`Catan.Server` 和相应测试项目。名称在实施时可以调整；这些工程当前尚不存在。Contracts 保持 Unity 兼容，只包含明确允许传输的消息，不暴露权威状态类型。服务器直接复用规则和 AI 程序集，无需运行 Unity 渲染或物理。

局域网版发布为自包含的 Windows `Catan.Server.exe`，由游戏启动和管理后台进程；在线版由同一服务代码发布为 Linux 服务。ASP.NET Core 不直接嵌入 Unity 的运行时，避免维护两套服务端实现。自包含发布会增加压缩包体积，运行时安全更新随服务重新发布。

首期采用单服务进程管理多个在线房间，每个房间一个顺序执行队列。存储并发和 AI 计算需做限额与压测，不预先引入多机房间调度、Redis 或每房间一个容器。多实例扩容时必须增加房间唯一写入者约束，不能让两个服务同时恢复并推进同一局。

## 两种联机流程

### 局域网

1. 玩家选择“局域网 → 创建房间”，客户端启动随包服务，等待健康检查成功后加入。房主客户端也按普通席位连接，不绕过权限校验。
2. 服务通过 UDP 响应局域网发现，只公开房间名称、人数、规则概要、版本和连接地址。发现报文不包含口令、令牌、存档或私有局面。
3. 其他玩家从房间列表加入，也可输入 IP。自动发现限于可达的局域网；手动 IP 不能绕过防火墙或 Wi-Fi 客户端隔离。
4. 使用加密连接传输私有视图。建议本地服务生成证书，由房主界面展示指纹供首次连接核对并固定；不得全局跳过证书检查或悄悄降级为明文。配对交互在接入切片验证。
5. 服务随游戏附带，无需玩家另装 .NET。启动失败、端口占用、防火墙阻挡和进程退出应有中文提示。正常结束房间后退出对应后台进程，不留下失控的服务进程。

局域网属于信任房主的环境：房主电脑持有完整权威状态，无法保证对电脑所有者隐藏手牌或随机状态。首期不把完整存档自动传给其他玩家换主；房主电脑关闭或服务停止时对局暂停，由原主机重新启动并恢复最后已提交的局面。

### 在线大厅

1. 客户端通过 HTTPS 建立身份会话并查询房间；创建时选择公开列出或仅房间号加入、密码、规则、剧本、人数与 AI 席位。
2. 服务生成房间标识，验证加入条件并分配席位。房间号和昵称都不能作为取回原席位的身份证明。
3. 玩家准备完成后由房主发起开始，服务器验证配置和席位，再创建权威规则会话。
4. 对局消息通过 WSS 连接云服务，玩家无需开放入站端口或配置路由器转发。
5. 房主离开时转交房间管理权，权威对局仍由服务器持有。缺席玩家的行动依房间掉线政策等待或交由 AI，不将“服务仍存在”误作“可以跳过必需选择”。

首期建议采用可持久保存凭据的轻量访客身份，以降低加入门槛；账号、跨设备恢复和凭据丢失后的处理方式待确认。无论采用何种方式，席位恢复都必须验证凭据。同一席位的新连接取得控制权时，应使旧连接失效，避免双端同时操作。

## 指令与状态同步

现有 [CombinedGameSession](../src/Catan.Core/M5GameSession.cs) 已提供 Execute、GetPlayerView、GetHistory、Save 和 Load；其他规则包按各自入口适配。新增网络层连接这些接口，不复制规则判定。

客户端只提交玩家意图，例如建造位置、交易报价和待决选择。服务器负责掷骰、抽牌和最终结算。棋子拖动、卡牌飞行、相机、物理和动画完成时间都不决定规则结果。

建议命令信封包含协议版本、房间 ID、唯一 CommandId、预期局面修订号和命令参数。服务端从已认证连接确定实际席位，不信任客户端自报的 PlayerId。回复包含命令确认或拒绝、已提交修订号、本人完整 PlayerView 及有权接收的新事件。

首期每次已提交操作后发送各自的完整可见视图，以降低增量合并复杂度；历史按游标分批获取，避免随对局无限增长的重复发送。消息大小、命令频率和发送队列设上限，慢客户端可断开后重同步，不能阻塞房间执行。网络收发不阻塞 Unity 主线程，界面更新回到主线程。

每个房间按以下顺序处理指令：

1. 验证协议、身份、房间归属、控制权和消息大小。
2. 查询已提交命令账本。同 ID、同席位且相同内容返回原执行结果；同 ID 不同内容拒绝。先处理重试，再判断旧修订号，防止已成功的操作因回执丢失被误判为失败。
3. 对新命令检查修订号、当前权限和待决条件，经对应规则 Execute 执行。过期指令不盲目重放，返回最新本人视图供玩家重新决定。
4. 将新权威快照、修订号、命令去重结果及必要恢复元数据作为同一事务写入存储。
5. 持久化成功后才确认成功并发送视图。写入失败时禁止发布内存中的未提交结果，暂停房间并回到最后持久状态；恢复后再接受操作。

广播交易可能同时收到两个接受请求，也可能与撤回竞争。顺序队列和执行时校验必须保证只结算一次；失败请求不能重复收付资源。多个玩家的弃牌等待决也必须逐条验证，不能只允许当前回合玩家发送命令。

## 隐藏信息与身份边界

网络输出采用字段白名单，并按收件席位生成。本人手牌、规则允许的临时窥看信息和私有历史仅发送给对应玩家；其他玩家只得到规则允许的数量、公开信息与事件。大厅只保存组队所需元数据。

权威 GameState、完整存档、成功命令原文账本、牌库顺序、未揭示地图和随机状态留在服务端。不得把它们发送到客户端后仅靠 UI 隐藏，也不得写入公开日志、错误信息或对局下载接口。公开校验不得使用完整权威状态的哈希代替可见视图校验。

本地人类、远程玩家和 AI 共用 Execute；AI 仅接收其席位的 PlayerView。服务端不得因能访问完整状态而给予 AI 更多信息。临时窥看权限结束后，客户端须清除过期界面缓存。

服务还需具备连接和请求限额、口令安全存储、身份令牌过期与吊销、私有存档访问控制及不含敏感内容的日志。在线证书正常校验；局域网证书配对失败应阻止连接。

现有 [RandomState](../src/Catan.Core/M5Models.cs) 标识为 `xorshift32-rejection-v1`，不能把“不发随机种子”等同于密码学不可预测。面向陌生人的公开运营前，应评估公开结果反推隐藏随机状态的风险；如需升级随机源，须单独设计算法版本、存档兼容和重放验证，并按规则变更要求测试。网络接入本身不静默改变既有随机算法。

## 掉线与存档继续

| 情况 | 预期行为 |
| --- | --- |
| 操作已执行但回执丢失 | 原 CommandId 重试只返回已有结果，不再扣费、掷骰或抽牌 |
| 普通客户端掉线 | 保留席位和待决；界面显示重连状态，禁止离线推进权威局面 |
| 玩家恢复连接 | 验证原席位凭据，恢复本人完整视图和待决，按需补齐授权历史 |
| 在线房主退出 | 转交管理权；棋局保留，缺席行动按预设政策处理 |
| 局域网主机关闭 | 其余玩家等待；原主机载入已提交存档后重连，不承诺无缝换主 |
| 云服务进程重启 | 从持久化恢复房间及命令账本，玩家重连；不从客户端上传的局面恢复 |
| 所有人离线 | 暂停并保存；保留期限和清理提示由明确的运营配置控制 |

本轮已确认等待断线玩家，已落地的 AI 席位在开局前设置；不自动把掉线人类转为 AI。存档不自动删除。跨设备身份找回和中途托管仍未实施；若后续启用，必须在命令边界交接控制并另行验证。

房间存档外壳记录协议版本、房间存档格式、规则与场景版本、席位身份映射、控制方式、房间设置、提交修订号及命令去重记录，内含规则层权威存档，包括待决与随机状态。身份凭据按专门的安全存储方式处理，不混入可分享的对局数据。恢复先完成完整性与兼容性验证，失败时保留原档并暂停，不能用新局覆盖。

本地单人旧档导入联机房间不是首版必需能力。M7 的“存档继续”首先指 M7 创建的同一房间恢复；若后续支持旧档导入，须另行处理原席位授权和已被本地玩家看到的秘密。

## 现有客户端的改造位置

当前 [M5App](../Unity/Catan/Assets/Scripts/M5App.cs) 的 Submit 同步返回并立即读取本地视图，目标预览也会直接调用权威 Host。联机接入应抽出异步客户端接口，将“等待确认、已确认、被拒绝、正在重连”明确反映到操作界面；不能仅给现有同步函数套一层 Socket。

预览优先使用服务端已提供的合法目标和 LegalActions，本地只做显示推导。必要的复杂预览采用受权限约束的异步请求，避免每帧网络往返。所有落子仍在提交时重新验证；旧视图产生的操作可能被拒绝并刷新。

[M6App](../Unity/Catan/Assets/Scripts/M6App.cs) 中的 AI 调度需从 MonoBehaviour 提取到房间逻辑。依据实际待决席位调度，保留当前策略，并与 [M6 权限约束](M6_ARCHITECTURE.md)一致。联网游戏不因某个客户端正在播放骰子动画或打开菜单而暂停整个服务；动画按已确认事件在本地排队。

## 实施顺序与交付物

以下为原方案的任务拆分，当前各项实现与通过范围见验收记录。每步保持现有单人模式可玩；本机检查不能替代其中的真实网络和清洁环境验收。

| 编号 | 工作 | 可交付结果与检查 |
| --- | --- | --- |
| M7-01 | 协议与共用房间逻辑 | 消息白名单、身份到席位绑定、异步接口、顺序队列；非法命令、重复命令和权限独立案例 |
| M7-02 | 基础版局域网切片 | 自包含服务启动、发现与 IP 加入、证书配对、选座准备；多个独立客户端完成基础版对局 |
| M7-03 | 四类规则与当前 AI | 全部现有剧本和 3／4 席配置可接入；交易及扩展待决不会卡死，单人模式无回归 |
| M7-04 | 在线大厅 | 云端同代码服务、房间列表／房间号／密码、身份会话、房主管理权转交；跨真实网络连接 |
| M7-05 | 持久化与恢复收口 | 覆盖命令提交各故障点、断线／重启／全员离线、托管边界和版本不兼容 |
| M7-06 | 独立验收与发布验证 | .NET 测试、Unity 构建、真实多机与广域网完整局、长局与负载检查、清洁环境解压运行 |

幂等、权限和持久化从 M7-01 开始设计并随切片落地，M7-05 是故障覆盖收口，不能等到大厅完成后才补这些基础机制。云端部署前需选定服务商、地域、域名与预算；无部署条件时可以交付已验证的局域网切片，但不能据此宣称 M7 全部完成。

## 验收标准

| 类别 | 必须通过的检查 |
| --- | --- |
| 完整对局 | 局域网与在线分别使用独立客户端，基础版、航海家、城市与骑士、组合均完成开局到胜利；3／4 席、纯人类和人类＋AI 均有覆盖 |
| 剧本兼容 | 所有当前支持的剧本和人数配置经网络适配器验证；工程全配置检查与真实多机代表局分别记录 |
| 非法操作 | 伪造席位、跨房间命令、非己方待决、过期视图、同 ID 不同内容均被拒绝且状态不变 |
| 并发与重试 | 广播交易多人接受、接受与撤回竞争、连续点击、回执丢失、旧连接重放不造成重复结算 |
| 隐私 | 检查各席位实际序列化输出、历史、错误、日志和重连回复；不存在越权手牌、牌库、迷雾或随机状态 |
| 恢复 | 弃牌、交易、金矿、进步卡、蛮族选择等待决流程中断后恢复；提交前／后崩溃结果明确，已确认动作不丢失 |
| 不变量 | 合法及非法操作后资源、棋子与供应守恒；网络恢复结果与最后已提交权威状态一致 |
| 环境 | Unity 6000.3.25f1 Windows 构建；目标发布后端实测；未装 .NET 的清洁机器能启动随包服务 |
| 网络 | 外网断开时 LAN 仍可用；跨网络在线连接；延迟、断连、发现受阻、端口冲突与慢客户端有可理解的处理 |
| 长局与容量 | 记录实际硬件、并发房间数、AI 占比、对局时长、内存和响应延迟；不以理论估算替代测试容量 |

规则修改须补独立案例、非法操作和不变量测试；代码修改须运行相关 .NET 测试并验证 Unity 兼容性。工程自动检查、真实窗口操作和用户本人试玩分别登记。M7 验收记录应列出实际通过项、失败项及未验证项，满足阶段退出条件后才更新 ROADMAP，并提交、推送实现与证据。

## 选型依据与待定事项

独立规则核心使纯 .NET 服务能够复用现有规则与 AI；回合制操作适合可靠消息传输和逐操作保存。该方案需要自行维护连接、身份、数据库备份、部署与监控，但在线对局的存活不依赖某位玩家的电脑，也不要求玩家安装 Steam。

Unity Lobby＋Relay 可提供组队和中继连接；Relay 不执行本游戏规则。Unity 当前支持主机选举与数据迁移，但选举本身不迁移游戏状态，仍需设计快照和隐私边界。因此本项目优先选择云端权威房间，不将主机迁移作为在线长局恢复的前提。

- [微软 .NET 支持周期](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)：服务端建议采用 .NET 10 LTS，并跟进维护补丁。

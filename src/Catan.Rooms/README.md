# M7 权威房间核心

`RoomDirectory` 是服务端唯一的房间操作入口，不引用 Unity。共用协议位于 `Catan.Network.Contracts`，编译目标为 .NET Standard 2.1。规则与 AI 沿用现有实现；联机层不重新解释规则。

## 消息与权限

`NetworkRequest.Operation` 区分大小写：`List`、`Describe`、`Create`、`Join`、`Reconnect`、`Get`、`History`、`Seat`、`Ready`、`Configure`、`Start`、`Command`、`Preview`、`Leave`、`Transfer`、`Recover`、`Revoke`。`Payload` 使用 `WireJson` 编码对应 DTO；`Command` 和 `Preview` 只解码选中规则包的具体命令类型，不接受类型名。规则包标识为 `base`、`seafarers`、`cities-knights`、`combined`；旧工作名称 `cities` 仅作为输入别名正规化。

`Create`、`Join`、`Reconnect` 必须提供当前客户端预期的规则版本和场景版本。可从 `NetworkProtocol.RulesVersion` 和 `NetworkProtocol.ScenarioVersion` 取得，不能仅将服务端返回的未知版本原样回传。`Describe` 可查询未公开列出的房间号码，仅返回公开房间摘要。

每个房间的人类席位具有独立随机凭据，服务端只持久化其 SHA-256；密码使用 PBKDF2-SHA256、随机盐与 100,000 次迭代。凭据默认有效 180 天，服务程序可经 `RoomDirectoryOptions.CredentialLifetime` 明确调整。凭据与昵称、房间号相互独立。重连替换连接控制标识，旧连接不能操作或获取视图。

产品客户端在首次 `Create`／`Join` 请求前生成并安全保存 `EnrollmentId` 与 32 字节随机 `EnrollmentCredential`，重试保持这两项和原申请内容不变。服务端将凭据 hash、申请编号、内容指纹与房间／席位在同一事务保存；丢失首次回执或服务重启后仍可重复原申请，取回同一房间与席位，不重复占位。内容指纹使用恢复凭据作为 HMAC-SHA256 密钥，避免含口令申请产生额外的快速口令猜测校验值。相同标识或凭据用于不同内容会被拒绝；过期、已离开大厅或已吊销的身份不能借重试复活。

该流程的响应不回传恢复凭据，客户端使用发送前已保存的凭据；重复响应中 `IsDuplicate` 为 `true`，`CommittedRevision` 为原申请的提交版本，其他视图为当前可见状态。无 `Enrollment` 字段的旧验证驱动仍可使用原握手；这种兼容流程不具备首次回执丢失恢复能力。

大厅 `Leave` 释放席位并撤销凭据；已开始的房间 `Leave` 保留原凭据与待决，以便恢复。`Revoke` 显式永久吊销凭据，已开始的席位仍保留等待，不自动交给其他玩家。凭据遗失、到期或吊销后的人工找回和跨设备恢复不属于当前能力。

## 顺序执行与保存

每个房间有独立执行锁。新指令先认证，再查询命令账本，然后检查修订号；相同 ID、席位和规范化内容返回原执行结果及最新本人视图，不重复执行。同 ID 的不同内容或席位被拒绝。命令中的玩家 ID 必须与已认证席位相符，最终执行 ID 和席位由服务器绑定。

首期使用原子房间文件作为事务存储：完整规则存档、修订号、凭据映射和命令账本同在一个私有文档中，先写同目录临时文件并 `Flush(true)`，再以 `File.Replace` 提交。新房间使用同目录 `File.Move`。这代替方案中的 SQLite 选型，避免引入额外本机运行依赖；`IRoomStorage` 留有后续数据库替换边界。

保存失败时回滚内存到最后已提交存档，暂停操作；不发送未提交成功结果。管理员可用 `Recover` 验证保存重新可用，或重启服务恢复。持久化目录持有独占文件锁，阻止两个实例同时写入。无法验证的存档会使恢复失败，并保留原文件，不能用新局覆盖。当前检查覆盖进程重启和注入的保存失败；突然断电与底层文件系统、磁盘缓存的持久性仍须在目标部署环境单独验证。

## 视图、历史与 AI

网络只序列化所属席位的 `PlayerView`，不序列化权威存档。快照最多保留 37 条真实公开事件：最后 32 条、最近回合边界和本回合各席最近一次报价。这样可保留当前 AI 的报价判断依据，而不重复发送无限增长的历史。完整有权限历史经 `History` 独立分页，每页 1–200 条。

服务端 AI 始终取得自己的完整 `PlayerView`，使用当前唯一 AI 策略，经同一规则 `Execute` 入口执行。调度按真实待决席位选择；开局后离开、断线或心跳超时的人类由 AI 接管，全员离线仍继续对局。重连可立即查看自己的局面，直到下一次自身行动回合才恢复操作，包含蛇形开局的下一轮摆放。`HumanControlAvailable` 表示当前绑定真人是否可以提交命令，`SeatSummary.ControlledByAi` 和 `RejoinPending` 提供公开状态。重试已提交命令仍优先返回原始回执。管理权可主动移交，也会在断线或心跳超时后交给仍在线的人类；它不改变服务器的权威所有权。

最后一位大厅玩家明确离开后，该大厅房间结束；断线大厅席位在连接超时后回收，空大厅结束。公开房间列表只显示有在线真人且尚未结束的房间，历史权威存档和身份申请回执保留。开局后的原玩家仍可凭所属房间的访客凭据重连。配置 AI 席位的中文名字从四个指定名字随机且不重复分配，并随房间保存。

已保存房间不自动删除。默认限制 128 个房间、每条请求 64 KiB、每个房间 100,000 条人类命令结果；人类与 AI 合计成功执行的规则命令同样不得超过规则存档的 100,000 条恢复上限。请求频率、TLS、物理连接绑定与日志安全由 `Catan.Server` 处理。未经实际负载测试，不将这些限制视为已经验证的容量承诺。

## 验证入口

加载工程开发环境后运行 `dotnet test tests/Catan.Network.Tests/Catan.Network.Tests.csproj`。测试覆盖所有 26 种规则／剧本／人数配置的房间开局，身份、重连、准备、管理权、并发、幂等、过期修订、保存失败、重启待决、失效凭据、输出类型与序列化隐私。完整在线 HTTP／WS、局域网 HTTPS／WSS 进程验证和 Unity 可玩构建由上层交付记录另行登记。
